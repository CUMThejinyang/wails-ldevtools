## 一、它是什么？

**Superpowers** 是一套安装在 Claude Code 里的"工作方法论插件"。

它把优秀的软件工程文化（先设计、先写测试、先找根因……）以 Markdown 文件的形式注入到 AI 的工作流中，**强制 AI 遵守规范**，而不是一拿到任务就直接开始写代码。

### 一句话总结

> **没有规矩的 AI 是危险的；Superpowers 就是给 AI 立规矩的工具。**

### 安装方式

```bash
/plugin install superpowers@claude-plugins-official
```

安装后新开一个 Claude Code 会话，技能自动生效。

## 二、为什么需要它？

### AI 不用 Superpowers 时会怎样？

| 场景 | AI 的默认行为 | 结果 |
|------|--------------|------|
| 你说"加一个搜索功能" | 立刻开始写代码 | 写出来的不是你要的 |
| 遇到 bug | 随机尝试修改 | 改了 3 次还没好 |
| 声称"完成了" | 没有运行验证 | 其实有问题没发现 |
| 代码审查有建议 | 立刻全部接受 | 引入了不适合项目的代码 |

### 用了 Superpowers 之后

- 先问清楚需求，再动手
- 先写测试，再写实现
- 先找根因，再修复 bug
- 先跑验证命令，再说"完成了"

## 四、核心工作流（从需求到上线）

每次开发一个新功能，标准流程是：

```
你提出需求
    │
    ▼
【brainstorming】需求分析 & 方案设计
    │ (你批准设计方案)
    ▼
【writing-plans】编写详细实现计划
    │ (二选一执行方式)
    ├──【subagent-driven-development】推荐！自动派子 AI 执行+审查
    └──【executing-plans】手动，每步你都可以介入
    │ (所有任务完成)
    ▼
【finishing-a-development-branch】
选择：本地合并 / 创建 PR / 保持现状 / 丢弃
```

### 贯穿全程的三个习惯

- **写代码时**：遵循 `test-driven-development`（先写测试）
- **遇到 bug 时**：遵循 `systematic-debugging`（先找根因）
- **说"完成"前**：遵循 `verification-before-completion`（先跑验证）

### 技能 1：`brainstorming` — 需求设计

这是**最重要的一个技能**，也是整个流程的起点。

#### 核心铁律

> 设计方案没有获得你的批准之前，**不能写任何代码**。

#### 9 步流程

```
第 1 步：探索项目上下文（看代码、文档、git 历史）
第 2 步：如有视觉问题，提供原型（独立消息）
第 3 步：每次只问一个澄清问题（优先选择题）
第 4 步：提出 2-3 种方案 + 权衡分析 + 推荐
第 5 步：分节展示设计，获得你的批准
第 6 步：编写设计文档到 docs/superpowers/specs/
第 7 步：规格自检（扫描占位符、矛盾、模糊点）
第 8 步：请你审查书面规格
第 9 步：调用 writing-plans 开始计划
```

#### 实际对话示例

```
你：帮我加一个用户搜索功能

AI：先了解一下上下文...（探索代码）

AI：我有个问题：搜索是实时的（边输边搜）还是按回车后才搜？

你：按回车后搜

AI：好的。我有 3 种方案：
    方案 A：前端过滤已有数据（快，但数据量大时慢）
    方案 B：后端 API 搜索（准确，但需要修改后端）★推荐
    方案 C：全文检索服务（最强，但引入新依赖）
    
    我推荐方案 B，因为...

你：用方案 B

AI：（展示详细设计，获得批准后）
    设计文档已写入 docs/superpowers/specs/2026-05-02-user-search-design.md
    请审查后我们开始编写实现计划。
```

### 技能 2：`writing-plans` — 编写实现计划

把设计文档拆解成详细的、可执行的小步骤任务清单。

#### 计划文档格式

```markdown
# 用户搜索功能实现计划

**目标：** 为用户列表页面添加按名称搜索的功能

**架构：** 前端输入框 → 回车触发 → 调用后端 /api/users?q= → 展示结果

### 任务 1：后端搜索接口

**文件：**
- 修改：`src/api/users.ts`
- 测试：`tests/api/users.test.ts`

- [ ] 步骤 1：编写失败的测试
  ```typescript
  test('支持按名称搜索', async () => {
    const res = await request.get('/api/users?q=张三')
    expect(res.body).toContainEqual({ name: '张三' })
  })
  ```
- [ ] 步骤 2：运行测试，确认失败
- [ ] 步骤 3：实现最少代码让测试通过
- [ ] 步骤 4：运行测试，确认通过
- [ ] 步骤 5：Commit
```

#### 关键原则

- 每步只做 2-5 分钟的工作
- 每步必须有**实际代码**，禁止写"待定"、"TODO"
- 计划保存到 `docs/superpowers/plans/` 并 commit

### 技能 3：`test-driven-development`（TDD）— 测试驱动开发

先写测试，再写代码。听起来反直觉，但这是保证代码质量最可靠的方法。

#### 三步循环（红-绿-重构）

```
🔴 红灯
   写一个失败的测试（这时候还没有实现代码）
   运行它，确认它"正确地失败"
        ↓
🟢 绿灯
   写最少的代码让这个测试通过
   运行，确认通过，且其他测试也没有挂掉
        ↓
🔵 重构
   在保持测试全绿的前提下清理代码
   （消除重复、改名、提取函数等）
        ↓
   回到红灯，写下一个测试
```

#### 铁律

> 如果你先写了代码再写测试 → **必须删掉代码，从头开始**。

#### 为什么顺序很重要？

| 先写测试 | 后补测试 |
|---------|---------|
| 测试必然先失败（证明它在测东西） | 测试立即通过（什么都证明不了） |
| 回答"代码**应该**做什么" | 回答"代码**已经**做了什么" |
| 发现你忘掉的边界情况 | 只验证你记得的情况 |

#### 实际代码示例

```typescript
// 🔴 第一步：先写测试（此时 retryOperation 函数还不存在）
test('失败操作会重试 3 次', async () => {
  let attempts = 0
  const operation = () => {
    attempts++
    if (attempts < 3) throw new Error('失败')
    return '成功'
  }
  const result = await retryOperation(operation)
  expect(result).toBe('成功')
  expect(attempts).toBe(3)
})

// 运行：FAIL ✓（正确失败）

// 🟢 第二步：写最少实现代码
async function retryOperation(fn) {
  for (let i = 0; i < 3; i++) {
    try { return await fn() }
    catch (e) { if (i === 2) throw e }
  }
}

// 运行：PASS ✓
```

#### 常见借口 & 正确回应

| 借口 | 真相 |
|------|------|
| "太简单了，不用测" | 简单的代码一样会出 bug，测试只需 30 秒 |
| "我之后补测试" | 后补的测试立即通过，什么都证明不了 |
| "我已经手动测试过了" | 手动测试不可重复，代码改了还要再测一遍 |
| "删掉 X 小时的代码太浪费" | 保留没有测试保证的代码才是浪费（技术债） |

### 技能 4：`systematic-debugging` — 系统化调试

遇到 bug 时，**先找根因，再修复**。禁止随机猜测式修复。

#### 四阶段流程

**第一阶段：根因调查**

在尝试任何修复之前：
1. 完整阅读错误信息（别跳过！往往直接告诉你答案）
2. 稳定复现（每次都能触发吗？具体步骤是什么？）
3. 检查近期变更（`git diff`、最近的 commit）
4. 追踪数据流（这个错误值是从哪里来的？）

**第二阶段：模式分析**

- 在同一代码库里找相似的、正常工作的代码
- 对比正常和出问题的代码，列出所有差异

**第三阶段：假设验证**

- 提出一个**具体**的假设："我认为 X 是根本原因，因为 Y"
- 做最小化的改动来验证这个假设
- 每次只改一个变量

**第四阶段：实施修复**

1. 先写一个能重现 bug 的失败测试
2. 修复根因（不是症状）
3. 确认测试通过，且没有回归

#### 特别规则

> 如果尝试了 **3 次修复**都失败了 → 停下来，质疑架构，不要尝试第 4 次。

#### 对比：正确 vs 错误

```
❌ 错误做法：
"测试失败了，让我随便改改看..."
改了一处 → 还是失败 → 再改一处 → 又出新问题 → 两小时过去了

✅ 正确做法：
1. 读错误信息 → "期望 'hello'，得到 undefined"
2. 追踪数据流 → 发现 getGreeting() 没有 return
3. 假设：缺少 return 语句
4. 最小化验证：加上 return
5. 运行：PASS ✓  用时 10 分钟
```

### 技能 5：`verification-before-completion` — 完成前验证

在没有证据的情况下说"完成了"是不诚实的行为。

#### 门控流程（必须按顺序）

```
1. 确定：什么命令能证明这个结论？
2. 运行：完整执行命令（重新跑，不能用之前的结果）
3. 阅读：完整看输出，统计失败数，检查退出码
4. 判断：输出是否真的支持这个结论？
5. 只有这时：才能说"完成"
```

#### 禁止用词

- "应该能行"
- "大概通过了"
- "我有信心"
- "看起来对了"

#### 正确 vs 错误

```
❌ 错误：
AI："我修改了代码，测试应该能通过了。"
（没有运行，纯靠感觉）

✅ 正确：
AI："运行 npm test..."
[输出：34 passing, 0 failing]
"全部 34 个测试通过。"
```

### 技能 6：`using-git-worktrees` — 隔离工作区

为每个功能创建独立的工作目录，避免分支切换混乱。

#### 什么是 Git Worktree？

正常情况下，一个 git 仓库只能同时看到一个分支的文件。
Worktree 让你在**同一个仓库**里同时打开多个分支的文件夹。

```
myproject/              ← 你的主目录（在 main 分支）
myproject/.worktrees/
  ├── feature-search/   ← 同一仓库，在 feature/search 分支
  └── fix-login-bug/    ← 同一仓库，在 fix/login-bug 分支
```

#### 自动流程

1. 检查是否有 `.worktrees/` 目录，没有则询问你
2. 验证该目录已被 `.gitignore` 忽略（防止意外提交）
3. 创建工作树并切换到新分支
4. 自动安装依赖（npm install / pip install 等）
5. 跑一遍测试，确认初始状态干净

### 技能 7：`executing-plans` — 手动执行计划

加载计划文件，逐任务执行，每 3 个任务暂停审查。

适合你想**盯着每一步走**、随时可以插手的情况。

#### 流程

```
1. 读取计划，批判性审查（找依赖遗漏、不清晰的验证条件）
2. 有疑虑先报告，无疑虑创建任务清单
3. 每个任务：
   → 标记"进行中"
   → 按计划实现
   → 运行验证
   → commit
   → 标记"完成"
4. 每 3 个任务批量审查
5. 全部完成 → finishing-a-development-branch
```

### 技能 8：`subagent-driven-development` — 子智能体驱动开发（推荐）

为每个任务派遣一个全新的子 AI 执行，执行后自动进行两阶段审查。

#### 每个任务的流程

```
主 AI 派遣「实现子 AI」
    ↓
实现子 AI：写代码 + 写测试 + commit + 自检
    ↓
主 AI 派遣「规格审查子 AI」
    是否符合计划要求？
    ↓ 不符合 → 实现子 AI 修复 → 重新审查
    ↓ 符合 ✓
主 AI 派遣「代码质量审查子 AI」
    代码质量是否合格？
    ↓ 有问题 → 实现子 AI 修复 → 重新审查
    ↓ 通过 ✓
标记任务完成，进入下一个任务
```

#### 为什么推荐这个？

| 好处 | 说明 |
|------|------|
| 上下文干净 | 每个子 AI 从零开始，不被前面的混乱干扰 |
| 双重质量门 | 规格合规 + 代码质量，两道关卡 |
| 早发现问题 | 每个任务结束立刻审查，不积累 |
| 速度快 | 不需要等待，自动推进 |

### 技能 9：`finishing-a-development-branch` — 完成开发分支

代码写完之后的标准收尾。

#### 4 个选项

| 选项 | 做什么 | 适用场景 |
|------|--------|---------|
| 1. 本地合并 | 合并到 main/master，删除功能分支 | 个人项目，直接合并 |
| 2. 推送创建 PR | push 并自动创建 Pull Request | 需要团队 Review |
| 3. 保持现状 | 先不动，你稍后处理 | 还没准备好合并 |
| 4. 丢弃 | 删除所有内容（需输入 'discard' 确认） | 这个思路行不通 |

### 技能 10 & 11：代码审查（请求 & 接收）

#### `requesting-code-review` — 请求审查

**必须审查的时机：**
- 每个重要任务完成后
- 合并到 main 之前

**三类问题的处理：**
- `Critical`（严重）→ 立即修复，不继续
- `Important`（重要）→ 继续之前修复
- `Minor`（小问题）→ 记录，稍后处理

#### `receiving-code-review` — 接收审查

**核心原则：技术正确性 > 社交舒适度**

```
❌ 禁止：
- "好观点！让我立刻修改..."（敷衍附和）
- 收到反馈立刻全部接受（盲目执行）

✅ 正确做法：
1. 完整阅读，不急于回应
2. 验证建议是否适合本项目
3. 不明确的地方先问清楚
4. 有理由的错误建议，用技术理由反驳
5. 一次修改一项，逐个测试
```

## 七、新手上手路径

### 第一周：理解框架

- 读本教程，了解每个技能的用途
- 在小功能上体验完整的 brainstorming → writing-plans → executing-plans 流程

### 第二周：养成三个核心习惯

1. **写代码前先写测试**（TDD）
2. **遇到 bug 先找根因**（systematic-debugging）
3. **说"完成"前先跑验证**（verification-before-completion）

### 第三周以后：提升效率

- 使用 `subagent-driven-development` 让 AI 自动化执行
- 使用 `using-git-worktrees` 在多个功能间无缝切换
- 遇到多个独立问题用 `dispatching-parallel-agents` 并行解决

## 八、常见问题

**Q：技能是 AI 自动触发的吗，还是需要我手动说？**

A：大多数情况下是自动的。`using-superpowers` 在对话开始时生效，AI 会根据任务类型自动判断并调用合适的技能。你也可以直接说"帮我做头脑风暴"来手动触发。

---

**Q：所有功能都要走完整流程吗？太慢了吧？**

A：不是。以下情况不强制：
- 一次性原型/实验性代码
- 配置文件修改
- 简单的文字/注释修改

凡是要进 main 分支的**生产代码**，建议遵守完整流程。

---

**Q：TDD 真的更快吗？感觉先写测试很耽误时间。**

A：短期看，写测试确实多花了 10-20 分钟。但不写测试的代价是：
- 上线后出 bug，调试 2-3 小时
- 改别的功能时悄悄破坏这个，发现时代价更大
- 没有测试文档，新同事不知道这段代码做什么

长期来看，TDD 是净赚的。

---

**Q：我自己可以添加新技能吗？**

A：可以，使用 `writing-skills` 技能来创建属于你们团队的自定义技能，比如"代码必须通过安全扫描"、"所有接口必须有 OpenAPI 文档"等。

---

**Q：子智能体驱动开发（`subagent-driven-development`）和手动执行（`executing-plans`）怎么选？**

A：
- 想快速推进、让 AI 自己跑 → 用 **subagent-driven-development**
- 想每一步都亲自确认 → 用 **executing-plans**
- 在不支持子智能体的平台 → 只能用 **executing-plans**
