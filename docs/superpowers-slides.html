问题背景

没有 Superpowers，AI 会怎样？

你说的AI 的默认行为结果
"帮我加搜索功能" 立刻开始写代码 写出来的不是你要的
遇到 bug 随机猜测式修改 改了 3 次还没好

Superpowers 就是给 AI 建立工作规范的工具。
什么是 Superpowers

它是一套工程文化插件

本质

一组 Markdown 文件（技能），安装到 Claude Code 后，强制 AI 在关键节点遵守规范，而不是一拿到任务就直接写代码。

"把优秀工程师的工作习惯，变成 AI 必须遵守的规则。"

技能详解 01

brainstorming — 需求设计

铁律：设计方案没有获得你的批准之前，不能写任何代码。

9 步流程

1
探索项目上下文（代码、文档、git 历史）
2
如有视觉问题，提供原型（独立消息）
3
每次只问一个澄清问题（优先选择题）
4
提出 2-3 种方案 + 权衡 + 推荐
5
分节展示设计，获得你的批准
6
编写设计文档到 docs/superpowers/specs/
7
规格自检（占位符、矛盾、模糊点）
8
请你审查书面规格
9
调用 writing-plans 开始计划

实际对话示例

你：帮我加用户搜索功能

AI：[探索代码]

AI：搜索是实时的（边输边搜）
    还是按回车后才搜？

你：按回车后搜

AI：我有 3 个方案：
    A：前端过滤（快，但数据多时慢）
    B：后端 API 搜索 ★推荐
    C：全文检索（最强，新依赖）

    推荐 B，因为...

你：用方案 B

AI：[展示详细设计]
    [你确认后写设计文档]
关键：每次只问一个问题，避免信息过载
技能详解 02

writing-plans — 编写实现计划

核心原则

  • 每步只做 2-5 分钟的工作
  • 每步必须有实际代码
  • 禁止写 "待定"、"TODO"、"后续实现"
  • 保存到 docs/superpowers/plans/
  • 保存后 commit 到 git
计划的粒度举例：
✓ "编写失败的测试" — 一步
✓ "运行它确认失败" — 一步
✓ "实现最少代码让测试通过" — 一步
✓ "Commit" — 一步

计划文档格式

# 用户搜索功能实现计划

**目标：** 为列表页添加搜索功能

### 任务 1：后端搜索接口

**文件：**
- 修改：`src/api/users.ts`
- 测试：`tests/api/users.test.ts`

- [ ] 步骤 1：编写失败的测试
  ```typescript
  test('按名称搜索', async () => {
    const res = await get('/api/users?q=张三')
    expect(res.body).toContainEqual({name:'张三'})
  })
  ```
- [ ] 步骤 2：运行测试，确认失败
- [ ] 步骤 3：实现最少代码
- [ ] 步骤 4：运行测试，确认通过
- [ ] 步骤 5：Commit
技能详解 03

test-driven-development — TDD

铁律：如果你先写了代码再写测试 → 删掉代码，从头开始。没有例外。

红-绿-重构 三步循环

🔴
红灯：先写一个失败的测试
运行并确认它"正确地失败"（不是报错，是断言失败）
🟢
绿灯：写最少的代码让测试通过
不要过度设计，刚好通过就行
🔵
重构：在绿灯下清理代码
消除重复、改名、提取函数，保持测试全绿

为什么顺序很重要？

先写测试后补测试
测试必然先失败，证明它在测真实的东西 测试立即通过，什么都证明不了
回答"代码应该做什么" 回答"代码已经做了什么"
发现你没想到的边界情况 只验证你记得的情况

常见借口 & 真相

"太简单不用测"简单代码也出 bug，测试 30 秒
"之后补测试"后补的立即通过，没用
"手动测过了"不可重复，改代码就要重测
技能详解 04

systematic-debugging — 系统化调试

铁律：不做根因调查，不许提修复方案。
3 次修复都失败 → 停下来质疑架构，不要尝试第 4 次

四阶段流程

1
根因调查
读错误信息 · 稳定复现 · 检查近期变更 · 追踪数据流
2
模式分析
找正常工作的相似代码，列出所有差异
3
假设验证
提出具体假设，最小化测试，一次只改一个变量
4
实施修复
先写失败测试 → 修复根因 → 验证通过

对比：正确 vs 错误

❌ 随机猜测式修复
"测试失败了，让我随便改改看..."
改了一处 → 还是失败 → 再改一处 → 又出新问题
→ 两小时过去了
✓ 系统化调试
1. 读错误："期望 'hello'，得到 undefined"
2. 追踪：getGreeting() 没有 return
3. 假设：缺少 return 语句
4. 最小验证：加上 return → PASS ✓
→ 10 分钟搞定
技能详解 05

verification-before-completion — 完成前验证

铁律：没有新鲜的验证证据，不许宣称完成。

五步门控流程

1
确定：什么命令能证明这个结论？
2
运行：完整执行（重新跑，不能用之前的结果）
3
阅读：完整看输出，统计失败数
4
判断：输出是否真的支持这个结论？
5
只有这时，才能说"完成"

禁止用词

"应该能行" "大概通过了" "我有信心" "看起来对了" "应该没问题"

正确 vs 错误

❌ AI："我修改了代码，测试应该能通过了。"
（没有运行，纯靠感觉）
✓ AI："运行 npm test..."
[输出：34 passing, 0 failing]
"全部 34 个测试通过。"
技能详解 06

subagent-driven-development — 子 AI 驱动

为什么推荐这个？ 每个任务用全新的子 AI 执行，上下文干净，两层质检自动化。

每个任务的流程

→
主 AI 派遣「实现子 AI」
↓
子 AI：写代码 + 写测试 + commit + 自检
→
主 AI 派遣「规格审查子 AI」
?
符合计划要求？不符合 → 修复 → 重审
→
主 AI 派遣「代码质量审查子 AI」
?
代码质量合格？不合格 → 修复 → 重审
✓
任务完成，进入下一个

vs 手动执行计划

推荐程度★★★ 推荐★★

适合场景快速推进需要精细控制

技能详解 07

finishing-a-development-branch — 收尾

铁律：测试没通过之前，不提供任何选项。

完整流程

1
验证测试：跑测试套件，全部通过才继续
2
确认基础分支：是 main 还是 master？
3
展示 4 个选项（让你选择）
4
执行选择并清理工作树

4 个选项详解

选项做什么适用场景
1. 本地合并 合并到主分支，删除功能分支 个人项目
2. 创建 PR push 并自动创建 Pull Request 需要 Review
3. 保持现状 先不动，你稍后处理 未准备好
4. 丢弃 删除（需输入 'discard' 确认） 思路不对
技能详解 08

代码审查：请求 & 接收

requesting-code-review — 请求审查

AI 自动派遣专门的审查子 AI 进行代码审查。

必须审查的时机：

  • 每个重要任务完成后
  • 合并到 main 之前
  • 卡住时（换个视角）
问题等级处理方式
Critical 严重立即修复，不继续
Important 重要继续之前修复
Minor 小问题记录，稍后处理

receiving-code-review — 接收审查

核心原则：技术正确性 > 社交舒适度
❌ 禁止
"好观点！让我立刻修改..."（敷衍）
收到反馈立刻全部接受（盲目执行）
✓ 正确做法
1. 完整阅读，不急于回应
2. 验证建议是否适合本项目
3. 不明确的点先问清楚
4. 错误的建议，用技术理由反驳
5. 一次修改一项，逐个测试

常见问题

Q & A

Q：技能需要手动触发吗？
A：大多数情况是自动的。using-superpowers 在对话开始时生效，AI 根据任务类型自动调用合适的技能。你也可以直接说"帮我做头脑风暴"来手动触发。
Q：所有功能都要走完整流程吗？太慢了？
A：不是。一次性原型、配置文件修改、简单注释修改不强制。凡是要进 main 分支的生产代码，建议遵守完整流程。
Q：TDD 真的更快吗？
A：短期多花 10-20 分钟，但不写测试的代价是上线后调试 2-3 小时。长期来看，TDD 是净赚的。
Q：subagent-driven 和 executing-plans 怎么选？
A：想快速推进 → subagent-driven；想每步亲自确认 → executing-plans；不支持子智能体的平台 → 只能 executing-plans。
Q：可以添加自己的技能吗？
A：可以，用 writing-skills 技能创建团队专属技能。比如"所有接口必须有 OpenAPI 文档"、"代码必须通过安全扫描"等。
Q：中文技能怎么启用？
A：项目有中文注释/README 或 commit 历史有中文时自动启用。建议中文项目确保 README 是中文的。
